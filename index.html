Copilot usage metrics, one line at a time

GitHub gives enterprise and organization admins daily Copilot usage reports as NDJSON files. This guide shows what is in those files, how the reports connect, how to get them, and what they can and cannot tell you.

  • NDJSON means newline-delimited JSON. Each line in the file is one complete JSON record.
  • The exports mirror the API output, so you can load them into BI tools and keep them for long-term reporting.
  • Each fact links to the public GitHub Docs page it comes from. Our own ideas and advice are marked as such.

Sources: Team-level metrics, Reconciling metrics

The six reports and how they connect

Each report comes at two scopes: enterprise and organization. Organization reports also carry organization_id. The reports differ in what one line stands for: a whole organization, one user, one team membership, or one repository.

Lines on the map show how the reports relate. A solid line is a safe connection. A dashed line is a connection that does not work.

Use it: adoption phases

          
Copilot puts each user into an AI adoption phase. A user is engaged with a feature when they use it on at least two different days in the last 28 days. GitHub checks the phases from the top down and gives each user the highest phase they qualify for. It calculates the phase again every day.

Count the right population

          
In the totals reports, each phase entry has two user counts. total_engaged_users counts users who were active on that one day. users_in_phase_28d counts everyone in the phase over the rolling 28 days. For a 28-day rate per user, the docs say:

          
    
            
  1. Add the daily total_pull_requests_merged values.
    2. 
            
  2. Add the matching daily users_in_phase_28d values.
    3. 
            
  3. Divide the first total by the second, then multiply by 28.
    4. 
          

          
Agent apps built by partners do not change a user's phase. Only the GitHub Copilot features listed above count.

Team metrics: build them with a join

          
There is no ready-made team report. You join the daily user-teams-1-day report with the daily users-1-day report on user_id, day, and the organization or enterprise ID. Then you group by team. Step through the example to see every row move.

Rules that keep team numbers honest

          
    
            
  • Join day to day. Do not join the 28-day per-user report with a one-day team snapshot. Activity goes to the wrong teams when membership changed.
    • 
            
  • Small teams are left out. Teams with fewer than 5 seated Copilot users that day are not in the user-teams report.
    • 
            
  • People on two teams count twice. For organization totals, use the per-user report without the join.
    • 
            
  • Count people, do not add them. For a multi-day window, use COUNT(DISTINCT user_id) over all joined rows. Do not add daily counts.
    •

Connect usage to delivery

          
Usage tells you who uses what. Delivery data tells you what shipped. The reports give you some delivery signals, but not per user.

          
    
            
  • Organization or enterprise: the pull_requests object in the totals reports gives created, reviewed, and merged counts and median time to merge, with Copilot cloud agent and code review splits.
    • 
            
  • Repository: repos-1-day adds review stage times and whether developers acted on Copilot code review comments.
    • 
            
  • By phase: totals_by_ai_adoption_phase gives pull request averages for each phase.
    • 
            
  • Per user: per-user reports have no pull request data. The docs suggest joining on user_login with data from the REST API endpoints for pull requests.
    • 
          

          
Compare periods and groups, then ask why. A difference between groups is an association. It does not show that Copilot caused it.

Limits: read these before you present numbers

          
The data is useful for trends and enablement. It is not complete, and it is not a score for people.

        

        

          
SourceReconciling Copilot usage metrics

        

      

      

        

          
Telemetry gaps

          
Detailed breakdowns need IDE telemetry. If a developer turns it off, or a proxy blocks it, the user can still count as active, but feature, language, and lines-of-code data stay empty.

          
Missing usage data

        

        

          
CLI is counted apart

          
Copilot CLI usage does not add to IDE active-user counts or other IDE metrics. The dashboard charts do not include CLI usage.

          
Reconciling: prerequisite

        

        

          
Two-day delay

          
A day is complete within two full UTC days. A drop in the most recent days is often only late data.

          
Delayed telemetry

        

        

          
Numbers do not add up across scopes

          
One user can appear in many organizations but only once in the enterprise. Do not add organization totals to get an enterprise total.

          
Organization attribution

        

        

          
Unknown and capped values

          
Unknown values are expected when the IDE cannot tell the language, mode, or model. Customization arrays keep 25 named entries, then group the rest as other.

          
Unknown values

        

        

          
Association, not causation

          
The adoption multiplier compares different groups of people. Team mix, project type, and seniority can matter as much as Copilot.

          
Adoption multiplier

        

        

          
No ROI in the files

          
Return-on-investment estimates are only in the impact dashboard. They are estimates, not financial results, and they are not in the API or NDJSON.

          
Impact dashboard metrics

        

        

          
Not a productivity scorecard

          
The docs warn against using the multiplier as a standalone measure of productivity, or any single peer value as a target. Our advice: do not use these files to rank individual developers.
